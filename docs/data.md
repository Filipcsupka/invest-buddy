# Data storage and daily scoring

Set `DATABASE_URL` and run `npm run migrate`. Numbered SQL migrations run once under an advisory lock. Migration 003 seeds the published instrument universe so an incoming symbol can be checked before the first daily score.

Set `DATA_MODE=db` for the scan pipeline. The runner posts a versioned payload to `/api/ingest/scan` with `INGEST_TOKEN`; it has no database access. A repeated `runId` returns a replay response. A later run for the same date and symbol supersedes the earlier finding while keeping its history. Claims without matching HTTPS evidence, unknown values, and low-confidence ticker findings add no points. The score audit includes the scan run ID and evidence URLs.

Run `npm run daily` after a scan. The job uses the latest current finding for each symbol, the latest macro finding, and any price bars already in `daily_bars`. Without at least 200 bars, the engine records Insufficient data. There is no fixture price fallback in database mode. `DATA_MODE=fixture` uses the sample universe for local development; `npm run daily -- --memory` runs against an in-memory score repository.

For a local end-to-end sample, start the database, migration, and web with `docker compose up -d --build db migrate web`. Run `npm run scan:sample` to post one sample NVDA scan. The optional `DATABASE_URL=postgresql://investbuddy:local-only@localhost:55432/investbuddy npm run seed:local-bars` seeds 220 synthetic NVDA price bars for this local demonstration. Then run `docker compose run --rm daily` and open `/en/dashboard`. The sample scan uses a public NVIDIA filings page as illustrative evidence; it is not a verified current research report. Finish with `docker compose down` to stop the containers while retaining the volume.

`GET /api/health` returns database reachability, the latest scan date, and the latest score date. It returns 503 when the database is unavailable. A Kubernetes readiness probe can use `/api/health`; a liveness probe should check that the web process answers an HTTP route without requiring a current scan. An empty database is reachable and returns 200 with null dates, so freshness monitoring must inspect the dates separately.
